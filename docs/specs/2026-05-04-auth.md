## Goal

Cho phép user tạo tài khoản, đăng nhập (email/password hoặc Google), và tự động đăng nhập lại khi mở app. Đây là foundation block — mọi feature khác đều require auth.

---

## User stories

- Là user mới, tôi muốn đăng ký bằng email/password qua flow 5 bước để có tài khoản Meep.
- Là user Google, tôi muốn đăng nhập bằng Google để bỏ qua bước tạo password.
- Là user đã đăng nhập, tôi muốn app tự đăng nhập lại khi mở để không phải login mỗi lần.
- Là user quên mật khẩu, tôi muốn nhận email reset link để lấy lại truy cập.
- Là user, tôi muốn đăng xuất từ Settings để clear session.

---

## Scope

### In-scope (MVP)

1. **Intro screen** — 2 CTA: "Tạo tài khoản mới" / "Đăng nhập". Acceptance: navigate đúng route.
2. **Signup email/password — 5 screens:**
   - Screen 1: Nhập email (validate format)
   - Screen 2: Nhập password (≥8 ký tự, show/hide toggle)
   - Screen 3: Họ + Tên (2 field riêng, không empty)
   - Screen 4: Username (3-20 ký tự, `[a-z0-9_]`, unique real-time check)
   - Screen 5: Tìm bạn từ danh bạ (optional — có nút "Bỏ qua")
   - Firebase `createUserWithEmailAndPassword` + tạo Firestore `/users/{uid}` sau screen 4
3. **Google Sign-In** — bypass password screen, vẫn vào họ tên + username nếu user mới.
4. **Login flow** — Email → Password → home. Inline error tiếng Việt khi sai creds.
5. **Forgot password** — gửi Firebase reset email. Success toast; KHÔNG gating login.
6. **Auto-login** — `authStateChanges()` stream, redirect `/home` nếu có session khi khởi động.
7. **Logout** — gọi `signOut()` từ Settings (UI của Settings thuộc Tier 1; auth chỉ expose method).

### Out-of-scope

- Email verification gating (gửi nhưng không block login)
- Apple Sign-In (defer với iOS post-MVP)
- Đổi mật khẩu detail flow (chỉ reset link)
- Profile editing trong signup (defer Settings Tier 1)
- Contact list import thực sự (screen 5 chỉ UI placeholder "Bỏ qua")

## Technical approach

### Architecture

```
Presentation          Application              Data
─────────────────     ────────────────────     ──────────────────────
IntroPage             SignUpController          AuthRepository (abstract)
SignUpEmailPage        ├─ SignUpState           FirebaseAuthRepository (impl)
SignUpPasswordPage     └─ step enum             UserRepository (abstract)
SignUpNamePage                                  FirebaseUserRepository (impl)
SignUpUsernamePage     LoginController
SignUpContactsPage      └─ LoginState
LoginPage
ForgotPasswordPage    currentUidProvider
                      isSignedInProvider
```

**Router guard:** `main.dart` watches `currentUidProvider` → redirect `/home` nếu uid != null, `/intro` nếu null.

### Data model

**Firestore `/users/{uid}`** (tạo sau screen username):
```
{
  uid: string,
  email: string,
  firstName: string,
  lastName: string,
  username: string,       // lowercase, unique
  photoUrl: string?,      // null khi mới tạo
  createdAt: Timestamp,   // serverTimestamp()
  bio: string?,
}
```

**Firestore `/usernames/{username}`** (lookup ngược, đảm bảo unique):
```
{ uid: string }
```

Cả hai document được tạo trong 1 Firestore `batch.commit()` sau khi Firebase Auth user đã tạo xong.

**Storage:** Không dùng ở Auth. Avatar upload thuộc Settings Tier 1.

### Signup flow state (SignUpController)

```dart
enum SignUpStep { email, password, name, username, contacts }

@freezed
class SignUpState with _$SignUpState {
  const factory SignUpState({
    @Default(SignUpStep.email) SignUpStep step,
    @Default('') String email,
    @Default('') String password,
    @Default('') String firstName,
    @Default('') String lastName,
    @Default('') String username,
    @Default(false) bool isUsernameAvailable,
    @Default(false) bool isLoading,
    String? errorMessage,
  }) = _SignUpState;
}
```

`createAccount()` gọi sau khi `step == username` và `isUsernameAvailable == true`:
1. `FirebaseAuth.createUserWithEmailAndPassword`
2. `Firestore batch`: tạo `/users/{uid}` + `/usernames/{username}`

### Google Sign-In flow

- `signInWithGoogle()` → nếu user mới (`additionalUserInfo.isNewUser`) → navigate signup name + username
- User cũ → navigate `/home` trực tiếp

### Username uniqueness check

- Debounce 500ms sau mỗi keystroke
- Query `/usernames/{username}` — document tồn tại → taken
- Inline indicator: loading spinner → ✓ available / ✗ taken

## Security

### Firestore rules (thêm vào `firestore.rules`)

```javascript
// users collection
match /users/{uid} {
  allow read: if isAuthed() && (request.auth.uid == uid || isFriend(uid));
  allow create: if isAuthed() && request.auth.uid == uid
                && request.resource.data.keys().hasAll(['uid','email','firstName','lastName','username','createdAt'])
                && request.resource.data.username.size() >= 3
                && request.resource.data.username.size() <= 20;
  allow update: if isOwner(uid)
                && !request.resource.data.diff(resource.data).affectedKeys().hasAny(['uid','createdAt','email']);
  allow delete: if false;
}

// usernames lookup
match /usernames/{username} {
  allow read: if isAuthed();
  allow create: if isAuthed() && request.resource.data.uid == request.auth.uid;
  allow delete: if isAuthed() && resource.data.uid == request.auth.uid;
  allow update: if false;
}
```

### PII handling

- Email: stored Firestore `/users/{uid}.email`, không log, không expose qua analytics.
- `displayName` Firebase Auth chỉ dùng làm fallback; source of truth là Firestore.
- Firestore doc: không log content trong Cloud Functions.

### Rate limiting

- Login attempts: Firebase Auth built-in throttle.
- Username check: debounce client-side 500ms (không cần server rate limit ở MVP).

## Boundaries

### Always do

- `serverTimestamp()` cho `createdAt` — không dùng client time.
- Convert `FirebaseAuthException` → `AppError` tại repository boundary.
- Validate username format client-side (regex `^[a-z0-9_]{3,20}$`) trước khi query Firestore.
- Batch write `users` + `usernames` atomically.

### Ask first

- Username tồn tại khi Google Sign-In (race condition): hỏi anh trước khi implement tiebreaker logic.

### Never do

- Không trust `email` từ client trong Firestore rules — dùng `request.auth.token.email`.
- Không lưu password bất kỳ đâu ngoài Firebase Auth.
- Không log `email`, `displayName` trong production logs.

## Risks

- **Username uniqueness race condition:** 2 user check cùng lúc cùng username. Mitigation: Firestore transaction thay batch (accept slightly slower write).
- **Google Sign-In SHA-1:** release build cần SHA-1 thêm vào Firebase console. Debug SHA-1 đã được flutterfire configure thêm.
- **Firebase quota:** auth operations trong Spark → đã upgrade Blaze, không vấn đề.
