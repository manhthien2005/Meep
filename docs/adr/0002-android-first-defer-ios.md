# 0002. Android-first, iOS deferred post-MVP

**Date:** 2026-04-30
**Status:** Accepted
**Supersedes:** Implicit cross-platform assumption in ADR-0001.

## Context

Meep is a 4-dev student capstone with limited time, budget, and tooling. The original assumption was Flutter cross-platform = "free both platforms". Reality check:

- **Native widget** is the headline differentiator — but it requires **two separate codebases** (Swift WidgetKit + Kotlin AppWidget), not one. Flutter's cross-platform abstraction stops at the widget boundary.
- **Apple Sign-In** is required by App Store policy when an iOS app already supports Google/FB sign-in. Implementing it doubles auth complexity vs. email + Google alone.
- **iOS DevOps** is non-trivial: Apple Developer Program ($99/year), macOS build runner (10x cost on GitHub Actions free tier), APNs cert setup, Xcode signing, TestFlight workflow.
- **Team has no Mac** for local iOS dev/test/debug.
- **Capstone rubric** does not require cross-platform shipping (verified via mentor — to be reconfirmed before Phase 2).

The team estimates iOS support adds **~25-35% workload** to MVP across widget, auth, DevOps, and testing — without proportional value to the capstone evaluation.

## Decision

**Target Android only for MVP.** iOS targeting is deferred post-MVP.

Concretely:

- **Flutter codebase stays cross-platform-ready.** No `Platform.isIOS` removed, no platform-specific code paths deleted. `flutter create` keeps both `android/` and `ios/` folders.
- **Build / CI / distribution: Android only.** No `flutter build ipa`, no macOS runner, no TestFlight, no App Store Connect.
- **Native widget: Android AppWidget (Kotlin) only.** No Swift WidgetKit code in MVP.
- **Auth providers: email + Google.** No Apple Sign-In in MVP.
- **FCM: Android only.** No APNs cert, no iOS background notification setup.
- **`apps/mobile/ios/`** stays as-is (Flutter generates it; no harm leaving it). Don't add iOS-specific Swift code.
- **Documentation, rules, workflows** explicitly mark iOS paths as "deferred per ADR-0002" so future contributors know it's a deliberate scope choice, not an oversight.

When iOS comes back (post-MVP): a separate scoped task will revisit this ADR, re-enable iOS CI, implement Apple Sign-In + iOS WidgetKit + APNs.

## Alternatives considered

### Option A — Strict Android-only (delete iOS code paths)

Pros:
- Cleanest repo. No dead code referring to iOS.
- Forces the team to commit fully to Android.

Cons:
- Deleting `apps/mobile/ios/` requires `flutter create . --platforms=ios` to add it back later — extra friction.
- Loses the "cross-platform-ready" framing useful for capstone defense.

### Option B — Android-first, iOS deferred (chosen)

Pros:
- Keeps Flutter codebase architecturally cross-platform — capstone defense narrative ("MVP focuses Android first; architecture supports iOS").
- Zero cost to leave `ios/` folder generated by Flutter.
- Re-enabling iOS post-MVP is a scoped task, not a rewrite.

Cons:
- Some files mention iOS in passing — risk of confusion. Mitigated by explicit "deferred per ADR-0002" markers in code and docs.
- A new dev might still try to build for iOS by mistake. Mitigated by deploy workflow + CI explicitly skipping iOS.

### Option C — Status quo (cross-platform from day one)

Pros:
- Real cross-platform shipping if team can pull it off.

Cons:
- 25-35% workload increase the team cannot absorb in capstone timeline.
- Requires Mac + Apple Developer Program ($99) — unbudgeted.
- Adds tooling burden (macOS CI runner cost, Xcode debugging, APNs setup) that distracts from product work.

## Consequences

### Positive

- Smaller MVP surface → faster shipping, more time for polish.
- No Mac/macOS runner dependency → CI runs on Linux only (cheap, fast).
- Auth scope reduced to email + Google → simpler onboarding flow.
- Widget = single Kotlin codebase → 1 dev can own it end-to-end instead of needing Swift expertise.

### Negative

- App is unavailable to iOS users at MVP demo. Capstone evaluation must accept this scope.
- Some iOS-related references remain in code/docs (kept intentionally for future re-enablement). Risk of drift if not maintained.
- If mentor changes their mind and demands iOS, Phase 2 work explodes — re-enabling iOS is ~3-4 weeks of work (auth, widget, CI, signing, TestFlight).

### Neutral / unknowns

- If MVP succeeds and iOS becomes a priority post-capstone, this ADR will be revisited and superseded.
- Firebase backend is platform-agnostic — no change required when iOS is re-enabled.
- Flutter dependencies (`firebase_auth`, `home_widget`, `flutter_local_notifications`) all support iOS — no migration cost on the Dart side.

## Verification of decision

This ADR is **revisited** when:

- Mentor explicitly requires iOS for capstone scoring (Phase 2 trigger).
- MVP ships successfully with bandwidth to spare for iOS expansion.
- A team member acquires a Mac + Apple Developer Program.

Until one of these happens, treat iOS work as out-of-scope and reject PRs that add iOS-specific build/CI logic without an updated ADR.
